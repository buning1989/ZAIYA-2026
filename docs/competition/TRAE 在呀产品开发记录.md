## 4.1 项目整体开发流程

本项目是一个面向社会功能已受损青少年 / 年轻人群的陪伴式健康生活管理产品 Web Demo，从产品需求、页面设计、核心功能开发、演示数据搭建、交互优化、问题修复到部署上线，主要通过 TRAE IDE 完成。

整体协作分工明确：**我主要负责产品判断、需求设计和体验反馈**，包括产品原则制定、交互流程定义、文案把关、视觉风格定调、问题识别与验收；**TRAE 主要负责代码生成、页面开发、交互实现、问题排查和部署支持**，包括根据自然语言需求生成完整页面与组件、重构数据层、修复 bug、执行构建校验与提交部署。

项目并非一次生成完成，而是经过多轮需求下达、效果验证和持续迭代。开发脉络可清晰分为三个阶段：

1. **方向探索期（2026-06-26 至 07-01）**：先在 TRAE 中新建 `zaiya-ios-demo` 仓库，从旧微信小程序仓库筛选可复用的对话逻辑、API 动作设计与安全边界规则；随后为确定 Web 端视觉气质，用 TRAE 复刻参考站 tolans.com 的单页落地页，并密集试验 Rive 动画集成与背景抠图策略，最终沉淀出"极简、克制、工具感"的设计取向。
2. **骨架与核心功能期（2026-07-02 至 07-06）**：按《在呀ZAIYA_Web端骨架改造方案.md》正式创建 `webdemo开发` 项目，搭建落地页 8 区块 + Demo 容器，并在沉浸式手机框内逐个开发对话、缓解、共同在场、记一下、回头看看、帮我整理、夸夸自己、我的隐私、设置等模块。
3. **演示与打磨期（2026-07-07 至 07-15）**：开发小晨案例演示模式与自由体验模式，重构统一数据源，做数据一致性审计、视觉一致性审计、媒体性能优化，并完成 Vercel 部署。后三天（7-13、7-14、7-15）单日提交量从个位数上升到 40—109 次，体现出"前期搭骨架、中期补内容、后期抠细节"的典型节奏。

### 阶段一：项目起源与官网骨架搭建

**产品目标**

先探索产品形态与视觉气质，再按《在呀ZAIYA_Web端骨架改造方案.md》搭建可演示的 Web 骨架：脱敏参考站模板，生成落地页 8 区块与 Demo 弹层容器，作为后续所有功能开发的承载基础。

**向 TRAE 下达的典型需求**

> "构建在呀 Web 骨架：脱敏 + 着陆页 8 区块 + Demo 六屏。Demo 弹层用全屏覆盖、固定手机框，不引入 React Router 依赖。"

**TRAE 完成的开发动作**

- 方向探索期：新建 `zaiya-ios-demo` 仓库并从旧仓库 sparse-checkout 筛选参考文件；复刻 tolans.com 落地页，试验 Rive 动画集成与四角采样背景抠图，最终保留源文件效果不做采样；
- 骨架期：删除 18 个 `.riv` 素材与 Tolan 专用组件，重命名 package 为 `zaiya-landing`，新建 Logo 组件；
- 落地页按 8 区块生成：Nav/Hero/ProblemSolution/ClinicalFramework/CharacterDesign/Team/Vision/Footer，Hero 内嵌手机 App / 桌面小组件 / 智能手表三种产品形态轮播；
- Demo 层采用"纯组件状态 + 全屏 overlay"方案，避开新增路由依赖；
- 安装 addyosmani/agent-skills 的 5 个核心 skill 文件作为工程规则基座；通过 `gh repo create` 创建 GitHub 仓库（初名 `tolans-landing`，后改名 `webdemo`）并完成首次推送。

**最终结果**

落地页 8 区块与 Demo 容器在浏览器中可访问，"极简、克制、工具感"的视觉取向在探索期就已确立并贯穿全程，奠定了后续所有迭代的代码与部署基础。

### 阶段二：沉浸式 Demo 首页与一级功能开发

**产品目标**

在沉浸式手机框内把"在在"IP 作为视觉主体，开发首页主界面及其到三个一级功能（对话 / 缓解 / 共同在场）的样式与交互反馈，并补齐"更多入口"侧边栏，让 Demo 首页具备真实 App 的体感。全程不接 LLM、不接后端，只用前端 mock。

**向 TRAE 下达的典型需求**

> "在 PR #1 / 分支 zaiya-demo-polish 中开发首页内对话模式的样式与交互反馈，不接 LLM、不接后端、不改 Demo 后续页面、不改 Web 首页 Hero。"

**TRAE 完成的开发动作**

- 首页主界面：调整手机外框为浅灰色、主屏纯白底，图标仅保留线框，在在动画放大为视觉主体，修复 CSS 宽度百分比塌陷导致在在消失的问题；
- 对话模式：在 `AppMainSurface.tsx` 中用 `motion.div` 控制在在位置，对话文案浮在场景中无气泡容器，纯前端 mock 回复；
- 缓解模式：把 `mode` 状态扩展为 `home / dialog / reliefSelect / reliefPractice` 四态，Wind 图标点击直接进入缓解选择，长按通过 `LongPressExit` 组件（requestAnimationFrame 计算进度）退出；
- 共同在场式陪做：新建 `PresenceCharacterRive` 通用组件 + `presenceCharacters.ts` mock 6 个角色，开发场景选择与房间布局，进入房间后在在形象完全退出不渲染，让 6 个角色成为唯一视觉主体；
- 主页到一级功能的过渡动画：在在形象在位置移动的同时进行尺寸缩放（Spring 动效），提升视觉层级感；
- 更多入口侧边栏：从左侧滑出、不完全遮盖主页、右侧保留压暗的主页背景。

**最终结果**

沉浸式 Demo 首页具备真实 App 的多模式切换体感，在在形象在 home / dialog / relief / presence 之间平滑过渡，"更多入口"侧边栏作为后续所有二级功能的统一入口。

### 阶段三：「记一下」多模块分页记录流程开发

**产品目标**

把"记一下"下的情绪、服药、饮食、睡眠、活动、体重六类记录，统一改造为"一页一个判断、单选自动进入下一步、多选用底部确认、不展示完整大表单、不出现折叠展开"的低压力分页流程，降低低能量用户的认知负担。

**向 TRAE 下达的典型需求**

> "重构情绪记录模块为分页流程，一页一个问题。一级情绪用卡片，二三级用胶囊，单选自动进入下一步，多选用底部'下一步'。'自伤/危险想法'要触发独立安全流程，不要出现'跳过'，改用'暂不补充'。"

**TRAE 完成的开发动作**

- 先用三层页面结构（recordHome / sceneHome / recordFollowup）实现快速选择优先、一键记录优先的交互流程，后改为"用户主动完成一次结构化生活记录"的核心入口；
- 新建 `moodOptions.ts` / `sleepOptions.ts` / `mealOptions.ts` 等结构化配置文件，替换组件内硬编码选项；为六类记录分别生成独立 Wizard 组件，统一状态机与字段重置逻辑；
- 实现"先保存"低能量退出机制：用户完成第一项基础输入后可随时保存并退出；记录确认页主路径为"完成记录"，弱化修改 / 删除意愿；
- 实现 Web Demo 可体验的右滑返回上一项手势（只改记录填写页内部手势，不改浏览器路由）；自由输入作为"自定义选项卡"与结构化选项同层级展示，左滑出现编辑 / 删除；
- 补充语音输入交互流程（前端 mock，不调用真实录音 / 识别 API），实现输入框 4 个状态切换，并复用 `VoiceInputBar` 统一首页对话输入与"帮我整理"补充输入的语音形态；
- 新增"返回时如有未保存改动，弹出底部确认 sheet（继续填写 / 放弃并返回）"的全局规则。

**最终结果**

六类记录全部对齐"一页一判断"交互原则，确认页结构统一为"摘要卡只读 + 补充说明独立模块 + 单一主按钮"，并通过 `.trae/documents/记录确认页全局交互规范.md` 固化为后续模块的硬约束。

## 4.3 TRAE 的典型开发动作

以下 8 个动作最能体现 TRAE 在本项目中的价值，每个动作都解决了真实产品问题。

1. **根据产品需求快速生成完整页面骨架与交互**
   从"构建在呀 Web 骨架：脱敏 + 着陆页 8 区块 + Demo 六屏"一句话指令，一次性生成 8 个落地页区块与 Demo 容器，并自行决定"纯组件状态 + 全屏 overlay"路由方案以避免新增依赖；后续沉浸式首页的多模式切换也由 TRAE 自主设计 `mode` 状态机实现。

2. **把"记一下"六类记录统一重构为分页交互框架**
   抽取 `moodOptions.ts` 等结构化配置文件，让情绪 / 睡眠 / 饮食 / 服药 / 活动 / 体重六个 Wizard 共享同一套"一页一判断、单选自动进入、多选底部确认"的状态机，并把规则固化成全局规范文档；同时实现右滑返回、先保存低能量退出、语音输入 4 态切换等细节交互。

3. **将分散的页面 Mock 数据重构为统一人物数据源**
   识别到体验模式内部 `lookbackRecords.ts` 与 `constants.ts + records.ts` 两套并行数据源后，把 `records.ts` 从 617 行压到 48 行适配层，让所有统计从 `dailyRecords.ts` 实时派生，消除"同一人物同一周却互相矛盾"的问题。

4. **处理演示模式与自由体验模式的状态隔离**
   通过 `UnifiedDemoStage` + `DemoPhoneFrame` 把两种模式统一进同一舞台容器，模式切换用 opacity 与 position 动画（0.28—0.32s）过渡而不重挂载手机 Demo 组件，URL 参数 `?mode=guided/?mode=free` 用 pushState 同步不做整页刷新。

5. **修复自然周 / 最近七天 / 月视图之间的日期问题**
   先做只读审计输出 31 项问题清单，再按 P0→P1→P2 顺序修复：删除未来日数据穿越、统一 5 个日期基准为 `DEMO_CURRENT_DATE = 2026-07-15`、把固定剧情"两周后"叙事与"两个月使用时长"对齐、统一药物名称为喹硫平。

7. **对全局视觉、颜色、布局与组件一致性进行审计**

## 4.4 踩过的坑与解决方案

### 问题一：演示模式与体验模式日期基准冲突

- **问题表现**：体验模式内部存在两套日级数据源，`lookbackRecords.ts` 设 7-15 为当前日，`constants.ts` 设 7-17 为参考日；7-16 / 7-17 有完整记录形成"数据穿越"，固定剧情用"两周后"叙事却与"两个月使用时长"矛盾。
- **原因**：团队已在迁移过程中但未完成，旧设计（6-15 ~ 7-17）与新设计（5-16 ~ 7-15）并存，且分散在 30+ 文件。
- **TRAE 的处理方式**：先执行只读审计输出 31 项问题清单，再建立 `DEMO_CURRENT_DATE / DEMO_START_DATE / DEMO_FOLLOWUP_DATE` 三个统一常量，删除未来日数据，把 `records.ts` 改为适配层，重写 validators 校验关键节点一致性。
- **修复后的结果**：7-17 不再被识别为已记录日，7-15 是有记录的当前日，所有统计实时派生，演示与体验模式共享同一份事实数据。

### 问题二：演示模式与自由体验模式切换有页面跳跳感

- **问题表现**：两种模式各自独立挂载，切换时手机 Demo 组件被重挂载，视觉上像跳到了新页面。
- **原因**：旧架构 `GuidedDemoShell` 与 `FreeExperienceMode` 是两个独立容器。
- **TRAE 的处理方式**：新建 `UnifiedDemoStage` + `DemoPhoneFrame`，把两种模式统一进同一舞台，手机 Demo 居中保持不重挂载，故事面板与步骤按钮用 opacity / position 动画过渡。
- **修复后的结果**：模式切换变成同一舞台内的平滑过渡，URL 参数仍可同步且不触发整页刷新。

### 问题三：共同在场 Rive 动画丢失与角色抖动

- **问题表现**：共同在场房间内 6 个 Rive 角色动画不播放，角色尺寸过小，昵称每次渲染都在变。
- **原因**：统一硬编码 `animations` 和 `stateMachines` 名称与各 `.riv` 文件实际名称不匹配，导致动画无法播放。
- **TRAE 的处理方式**：在 `PresenceCharacterRive` 中通过 `onRiveReady` 回调动态获取并播放动画，兼容不同 State Machine 命名；用模块级变量稳定随机昵称，避免每次渲染重新生成。
- **修复后的结果**：6 个角色动画正常播放，昵称稳定不抖动，进入房间后角色成为唯一视觉主体。

### 问题四：呼吸法展开后无退出路径

- **问题表现**：用户在"缓解"主页展开呼吸法后，没有直接退出路径，只能完成或返回上一步。
- **原因**：旧版只有底部一个返回入口，且呼吸法卡片展开后会遮挡。
- **TRAE 的处理方式**：在"缓解"主页左上角新增固定返回箭头，无论呼吸法收起 / 展开 / 切换卡片都保持显示，点击后通过 `setMode("home")` 明确返回产品主首页，倒计时期间点击会先清理 timer、重置状态再返回。
- **修复后的结果**：呼吸法任意状态下都有清晰的退出路径，状态正确重置，不依赖浏览器历史。

### 问题五：色彩规范迁移后 build 失败（tsc 增量缓存掩盖类型错误）

- **问题表现**：全站色彩 token 从冷调值迁移到新规范值、清除组件硬编码色值后，`npm run build` 失败，报 `PrivacyPage.tsx` import 缺失。
- **原因**：`src/data/privacy.ts` 存在未提交的 `Contact` 类型重构，`PrivacyPage.tsx` 仍引用旧导出；上一轮 build 通过是因为 `tsc -b` 增量编译使用了缓存，本次编辑 `PrivacyPage.tsx` 使缓存失效暴露了问题。
- **TRAE 的处理方式**：用 `git stash` / `git stash pop` 验证问题根因，确认与色彩替换无关，先把工作区完整快照提交（含 WIP 标注）以便回滚，再单独修复 `privacy.ts` 的 `Contact` 重构。
- **修复后的结果**：build 恢复通过，色彩迁移与类型重构分离提交，避免问题纠缠。

### 问题六：ZaizaiVideo 在 React StrictMode 下请求被 abort

- **问题表现**：`/assets/zaiya/zaiya-transparent.webm` 在本地开发环境报 `net::ERR_ABORTED`。
- **原因**：React StrictMode 在开发模式下双挂载，叠加 AnimatePresence `mode='wait'`，导致 ZaizaiVideo 组件在请求未完成时被卸载。
- **TRAE 的处理方式**：在 `ZaizaiVideo.tsx` 中新增 `canLoadVideo` 状态，延迟到 useEffect 提交后才渲染 video 元素，避免卸载阶段的请求中断。
- **修复后的结果**：刷新页面与切换层级不再触发 abort 错误。

## 4.5 开发实践总结

回顾整个项目，TRAE 在「在呀 ZÀIYA」Web Demo 开发中体现了几个可复制的实践模式：

1. **产品判断与代码生成分工明确**。我负责定义产品原则、交互规则与验收标准（如"一页一判断""不出现'跳过'改用'暂不补充'""高风险操作才补充必要后果"），TRAE 负责把这些规则转化为可运行的组件与数据层。两者结合让产品原则真正落到代码里，而不是停留在文档。

2. **用参考站探索视觉气质，再沉淀为项目骨架**。在正式动工前，先用 TRAE 复刻 tolans.com、密集试验 Rive 动画与背景抠图策略，把"极简、克制、工具感"的设计取向从模糊偏好变成可复用的代码与组件约定，避免了后续开发中视觉风格的反复摇摆。

3. **"先审计、后修复"的问题处理路径有效**。面对数据一致性这类跨模块问题，TRAE 先做只读审计输出问题清单与优先级，再按 P0→P1→P2 顺序修复，避免了一上来就改代码导致的遗漏与回归。审计报告本身也成为后续验证的依据。

4. **检查点 + 构建校验是迭代节奏的保障**。每次重大改动前 TRAE 自动建立 Git 检查点，改动后执行 typecheck / lint / build 三连，使得在 7-14 单日 109 次提交的高强度迭代下，演示路径仍能稳定可演示，没有带着构建错误进入下一轮；遇到 tsc 增量缓存掩盖类型错误时，也能用 git stash 快速定位根因。

5. **统一数据源是演示可信度的地基**。演示类项目最容易在"同一人物在不同模块信息冲突"上翻车，本项目通过把所有日级事实收敛到 `dailyRecords.ts`、所有日期收敛到 `timeConfig.ts`，从根本上消除了跨模块矛盾，让评委在任意路径下看到的信息都自洽。

6. **体验反馈驱动持续微调**。从"小组件按压反馈时长 120-180ms"到"左右箭头位置在无手机框的阶段页也要一致"，大量细节是在实际体验后由我反馈、由 TRAE 调整的。这种"需求下达 → 效果验证 → 持续迭代"的循环，是 Demo 质量从"能跑"到"可演示"的关键。

整体来看，TRAE 在本项目中的价值不仅是"生成代码"，而是承担了一个能理解产品意图、能自主设计架构方案、能执行审计与修复、能完成部署校验的协作开发者角色，使一个 14 天内从模板脱敏到上线可演示的 Web Demo 成为可能。
